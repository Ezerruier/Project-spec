在新项目启动、选择日常维护流程或进入真实阶段交付时读取。核心约束见 [SKILL.md](../SKILL.md)；只执行当前场景适用的步骤。

## 新项目启动

1. 从用户目标和现有材料确认主工作目录、预期产出、输入来源与只读边界；能确定的事项直接推进，仅澄清会改变目标、权限或兼容性的缺失信息。
2. 检查目录是否确为新建、是否已在父级 Git 仓库内，以及已有目录职责和工具原生布局。按实际产出建立少量必要目录；无脚本、数据或图表时不预建对应空目录。
3. 写入或补充 README：项目目标、主目录定位方式、入口/运行方式、实际目录职责、数据口径与来源、关键依赖和输出位置。外部原始数据记录来源与获取方式，不因建骨架而复制入库。
4. 主动评估 Git 的适用性及 `.gitignore` 必要性，按 [Git 决策参考](git-decisions.md) 说明实际情况和建议。无仓库不强行初始化；不默认创建 `.gitignore`、首次提交或推送。忽略方案由用户裁决后执行，初始化和提交各自依据适用授权。
5. 验证当前入口与目录引用，交付可用起点及尚待决定的事项。等待 `.gitignore` 决定时，继续文档、源码等不依赖它的工作；只暂停受影响的提交。

目录可按需使用 `docs/`、`scripts/`、`data/raw/`、`data/processed/`、`figures/`、`src/`、`tests/` 及项目约定的临时目录；它们是职责示例，不是必须完整创建的清单。受控数据或大文件采用适用存储方式，并保留来源、校验信息和访问说明。

## 日常维护与小修改

1. 读取受影响文件、直接依赖及适用指令，确认工作区原有改动和保护边界；避免为单文件修改盘点整个项目。
2. 接到任务和发现新可拆分工作时，按 [多 Agent 协作参考](collaboration.md) 判断委派收益。单文件小修、强依赖或协调成本更高的工作直接完成；独立调查或复核值得并行时主动委派。
3. 只修改本次目标所需区域，沿用既有职责和风格。新增或修改脚本、文档时按 [编写参考](authoring.md) 补足适用的头部、参数、路径和元信息；不为规范化而批量重写历史文件。新增或修改可复用提示词时，按 `docs/prompts/` 归档并补元信息。
4. 做与改动相称的检查：文案修改复核内容和引用；行为修改验证受影响行为与边界；迁移检查引用和回退。可回退、低影响的小改无需专门新增一套测试或阶段报告。生成或修改文本文件后，运行 `scripts/check_text_health.py`；涉及 `.gitignore` 时加 `--gitignore`。未运行则说明原因与影响。
5. 在连贯改动完成、阶段交付或切换主题时，核实实际 Git 状态和验证结果，主动给出提交建议及准确范围。提交建议不代替提交授权，详见 [Git 决策参考](git-decisions.md)。

目录整理、历史清理或脚本迁移先转到 [既有工作区整理参考](workspace-organization.md)。不把日常维护自动升级为全量盘点、全流水线重跑或历史改造。

## 阶段交付与依赖验收

阶段是有明确产出、且下游将依赖它的实际工作环节，如数据解析、清洗、分析或图表定稿。核心产出完成、准备供依赖它的下一阶段使用时，先验收该产出；普通编辑步骤和每次委派不单独设置阶段门或审批。

| 验收维度 | 要核实的内容 |
|---|---|
| 目标 | 结果是否回答本阶段问题；分析主线及约定口径是否保持一致 |
| 结果 | 对影响结论的数字、代表样本或关键证据独立复核；选择必要的格式、数值和领域 QC |
| 完整性 | 按实际转换类型核对覆盖、遗漏、重复和异常去向；采用下表中适用的检查 |
| 衔接 | 下游需要的字段、文件、单位、格式和路径是否齐全可用；共享文件整合结果是否已验证 |

从结果反推目标并交叉核验关键项，不只复述实现逻辑。重跑前核实是否改写输入或覆盖受保护状态；目录整理验收不自动触发分析重跑。子 Agent 的完成声明只是待验收输入，主 Agent 仍需核实关键证据及集成结果。

| 转换场景 | 适用的完整性检查 |
|---|---|
| 同一计数单位下互斥且穷尽的筛选 | `输入数 = 保留数 + 剔除数`；各项只计一次，剔除原因与去向可追溯 |
| 去重 | 明确记录/实体的计数单位、重复判定键与每组保留规则；核对唯一键覆盖和重复项去向 |
| 多条聚合为一条 | 核对输入到分组的映射、分组键覆盖、组内计数及适用的总量守恒；行数无需守恒 |
| 一条拆分为多条 | 核对父子标识和映射覆盖，逐个父项检查预期子项数量、缺失与重复 |
| 连接或合并 | 核对键唯一性、预期连接基数、未匹配键及重复匹配引起的行数膨胀 |
| 逐文件移动或删除的目录迁移 | `基线数 = 留存的基线文件数 + 已授权删除数`；单位一致，移动不增计，新增报告、索引和备份单列；含合并、拆分或转换时核对来源到去向映射及记录覆盖 |

计数必须写明对象与单位；不满足公式前提时改用映射、键覆盖或适用守恒关系，不把聚合/拆分后的行数差认定为丢失。文件存在或数量正确也不能代替分析有效性检查。

通过后记录结论并开放对应下游；失败或存疑时说明具体影响，修正、补充验证、重分派或接手相关工作。依赖未通过验收的下游暂缓，其他独立工作继续。记录保存在 `docs/` 或项目既有阶段记录中，规模与风险相称，不为每个子任务生成独立文档。

## 阶段门文件命名与看板

- 阶段门文件统一命名为 `stage-check-<stage>-<YYYYMMDD>.md`，`<stage>` 用流水线阶段名（如 `search`、`screening`、`extraction`、`synthesis`、`submission`），不用章节号或卡片名代替阶段名。
- 章节/卡片级自检可保留，但归入 `docs/handbook/` 或对应阶段目录，并在阶段门中引用，不单独充当阶段门。
- `docs/audit/README.md` 维护 gate dashboard：`| 阶段 | 状态 | 日期 | 门禁结论 | 遗留 |`。
- 历史文件不批量重命名；新文件按新命名，旧文件在 dashboard 中登记即可。

## 阶段自检记录模板

按实际检查删去不适用栏目，保留结论、证据边界及影响下游的事项。元信息与 [文档编写要求](authoring.md) 一致。

````markdown
# 阶段自检记录 — {阶段名}

> 版本: v1.0.0
> 更新日期: {YYYY-MM-DD}
> 阶段: {阶段名}
> 检查日期: {YYYY-MM-DD}
> 检查人: {实际检查人}

| 版本 | 日期 | 修改说明 | 作者 |
|---|---|---|---|
| v1.0.0 | {YYYY-MM-DD} | {本次阶段验收范围} | {作者} |

## 目标与产出

- 阶段目标及关键交付物：{目标、路径或标识}
- 目标符合情况：{结果及依据}

## 实际检查与完整性

- 静态审查：{检查范围、证据和结论}
- 真实工具运行：{实际命令/操作、结果；未运行则写明}
- 场景推演：{推演输入、预期决策及局限；未做则删除本项}
- 完整性方法：{筛选闭环/分组覆盖/父子映射/连接基数/迁移基线等，含计数单位}
- 异常、遗漏或剔除项：{原因、去向和处理结果}
- 未执行或不适用检查：{原因及其对结论的限制}

## 下游衔接与结论

- 字段、文件、格式及路径：{已核实内容}
- 集成验证：{影响关键结论的证据与整合结果；无集成则注明}
- 结论：{通过/已修正后通过/未通过/存疑}
- 遗留问题与依赖影响：{问题、影响、下一步；无则写无}
````

## 按任务和风险选择自查

以下是选择表，不是所有任务必须逐项填写的固定清单；内部判断即可，小修改无需生成自查文档。已选检查若未做，在交付中如实说明原因与影响。

| 适用条件 | 要检查的内容 |
|---|---|
| 每项任务 | 目标和授权边界明确；本次改动范围正确；结论与实际证据相符，未将推演写成真实运行 |
| 新增或修改文件 | 目录职责和命名沿用约定；适用元信息、引用、编码及路径正确 |
| 脚本、参数或分析逻辑变化 | 读写边界、参数集中、根锚点与调用方式；关键行为及口径；不引入偏离主线的补丁目录 |
| 涉及数据、复制或跨位置工作 | 原始数据只读，工具是否原地改写已核实；来源与工作副本区分；同步清单和必要校验齐全 |
| 阶段产出将供下游使用 | 目标、结果、适用完整性关系、下游接口与验收结论已核实并记录 |
| 实际使用多 Agent | 分工和写入归属明确，依赖得到协调；主 Agent 已核验关键证据和集成结果 |
| 迁移、整理或删除 | 来源与依赖、精确授权、基线、迁移清单、路径适配及可恢复依据符合整理参考 |
| 新项目或新生成产物、忽略问题 | 已评估 Git 适用性及 `.gitignore`；实际忽略规则变更有适用用户决定和代表性匹配验证 |
| 连贯改动完成或其他提交判断节点 | 已区分本次/原有改动及暂存/未暂存/未跟踪状态；验证情况、提交建议、范围和理由准确 |
| 临时产物或审计记录 | 临时产物归位且清理遵守授权；必要日志和复现材料保留；审计记录按既有方式归档 |
