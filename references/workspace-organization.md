# 既有工作区整理参考

> 版本: v1.0.0
> 更新日期: 2026-10-29

| 版本 | 日期 | 修改说明 | 作者 |
|---|---|---|---|
| v1.0.0 | 2026-10-29 | 归纳历史工作区来源盘点、精确清理、可回退迁移与验收决策 | Codex |

用于已有目录整理、历史文件清理或脚本重分层。按实际风险选择检查深度；无需为少量可回退文档归档建立大型工具链。此参考不授予删除、修改原始数据或对外发布的权限。

## 先明确整理边界

识别主目录、根级条目、原始数据、受控材料、软件约定布局和当前 Git 状态。用户说“根目录不变”时，区分保留主路径与保留根级条目；可从上下文确定时直接执行，只有含义会改变实际操作范围才澄清。

已有授权可覆盖可回退的内部归类，无需对每次移动重复询问。用户要求“删除前询问”时，先把来源和影响做成可审阅清单，再请求具体删除决定；未答复不构成同意。根级变化、递归删除、重写历史或对外上传不能从一般“整理”请求自动推出。

## 只读盘点来源与依赖

先列文件和目录、大小及必要时间信息，不运行分析。检查脚本的读写路径、启动入口、说明中的引用和日志内容；追踪清单的生成者与读取者。需要时分工并行只读审查代码、文档/日志和数据布局，实际迁移保持协调。

| 要回答的问题 | 可用证据 | 决策含义 |
|---|---|---|
| 文件怎么来的？ | 实际运行日志、生成脚本、内容特征、已核实版本记录 | 区分已观察事实、代码意图与推测；创建时间/文件名只能作线索 |
| 是否仍被使用？ | 调用关系、默认路径、下游输入、文档入口 | 没搜索到引用不能单独证明无用；考虑软件隐式布局和外部调用 |
| 删除后能否重建？ | 保留源文件、脚本、参数、工具版本和运行条件 | 可再生不等于零成本；说明重跑时间、环境和独有历史信息损失 |
| 真是重复副本吗？ | 明确保留对象与内容哈希，必要时核实格式元信息 | 内容相同仍需判断两条路径是否分别承担软件输入职责 |

按目的与生成来源区分正式入口、历史方法决策、队列/来源元数据、实际运行日志、可再生调试产物及软件阶段数据。成功日志保留执行证据；失败日志可能包含独有故障信息，体积小不是删除理由。教程描述不等于实际执行记录。

## 先形成具体迁移和清理方案

在原有顶层职责下选择少量有用子层级，不按个人偏好重建全套目录。数据的被试、会话、阶段目录及配套文件通常应整体保持；通过 README 或索引解释，可避免破坏原生读取逻辑。

删除候选至少写明：具体相对路径、当前大小、来源及置信度、复现依赖、再生方式/条件、删除后失去什么，以及用户的决定。若由副本相同认定可删，记录保留对象和比较方式。来源未找到就写未找到；不把“疑似测试”写成已确认事实。

执行前核对解析后的源、目标和删除路径确实位于指定工作区，且目标无冲突。复核已获准文件的身份/内容是否变化；变化或范围不符即停止该项，继续独立安全工作。只删清单内对象，不顺带递归清空目录。

## 迁移、适配与回退

有批量移动或需编辑旧代码时，先保存基线清单与可恢复原件。优先使用已核实覆盖当前内容的提交；无提交或有未提交改动时，保存必要原件并校验，不把 Git 索引当备份。

迁移清单建议包含 `source`、`destination`、`bytes_before`、`sha256_before`、`sha256_after_move`；内容随后修改时，另记修改后哈希和原因，避免混淆纯移动与代码编辑。对移动的关键小文件适合逐项哈希；未移动的大数据可按风险选择元数据核验或内容哈希，并如实说明两者保证不同。不要无意义重读所有大文件。

脚本重分层需同时核实：项目根定位、命令行覆盖、输入/输出路径、清单生产与消费、日志位置、文档调用命令。路径替换后对照原件确认科学参数、队列和处理顺序没有被顺带改变；升级版本/日期。不要把旧脚本直接挪回旧位置而保留新根锚点。

回退方案应能恢复位置和必要原内容，避免覆盖迁移后新增工作；明确备份保留位置和清理条件。若有维护脚本，默认只读预览，执行使用显式开关；源不存在、目标冲突或快照不匹配时拒绝盲目重复迁移。只有规模和重复使用价值足够时才编写此类脚本。

## 验收与证据边界

分别统计基线保留/删除与新增产物：`基线数 = 留存的基线文件数 + 已授权删除数`，备份、索引和报告单独计数。移动同一文件不增加基线数量；内容合法变化需在清单中交代。

按修改范围核对迁移文件、受保护路径、字节与必要校验值，检查入口及所有已知生产/消费引用。若本次未授权修改 Git 状态，可对照索引状态；原暂存文件不能被本次默认纳入提交。新 `.gitignore` 也不会清除旧暂存。

不修改索引并不等于工作树没有 Git 交接影响。已暂存文件若被移动，说明旧路径暂存项与新路径未跟踪项之间的对应关系；优先保留正在准备提交的入口位置，以索引分类。确需迁移时展示预期状态，保留用户原改动，不擅自替用户重做暂存。

| 已完成的验证 | 可以支持 | 不能据此声称 |
|---|---|---|
| 文件存在、路径/大小/时间相同 | 这些元数据未变 | 内容逐字节相同、处理科学有效 |
| 内容哈希相同 | 对应时点文件字节相同 | 来源决策正确、分析参数合理 |
| 语法/AST 检查 | 已检查语言的语法通过 | 真实环境执行成功或所有语言通过 |
| 日志显示完成 | 该记录报告了完成 | 产物正确或视觉/数值 QC 通过 |
| 对照原件的参数检查 | 检查范围内参数保持 | 完整流水线已重跑复现 |

核实工具对工作输入的真实行为：有些流程会原地改写输入副本的头信息、数值类型或采样数量。记录上游原件与运行后副本的区别，依据实际格式元信息/处理记录追踪；不得仅按路径名或文件大小反推原始状态。整理验收通常只需静态检查，不应因此重跑会改写数据的流程。

历史报告发现问题时，保留原结论的时间和适用范围，加注历史局限并另列待复核项。最终说明写清已移动/删除什么、依据是什么、哪些检查实际执行、哪些没有执行，以及能否回退；“没有发现变化”需与检查深度匹配。
