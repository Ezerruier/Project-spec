# Git 与忽略规则决策参考

> 版本: v1.0.0
> 更新日期: 2026-11-08

| 版本 | 日期 | 修改说明 | 作者 |
|---|---|---|---|
| v1.0.0 | 2026-11-08 | 定义提交建议、暂存保护及 .gitignore 评估、裁决和验证流程 | Codex |

形成一组连贯改动、完成阶段交付、准备切换主题时读取提交部分；新项目启动、准备纳入 Git、出现新的生成产物或发现忽略问题时读取忽略规则部分。规则适用于主 Agent 和子 Agent；委派不扩大任何 Git、删除或发布权限。

## 先确认 Git 是否适用

先确认实际仓库根目录、当前分支、是否已有提交及工作树状态。没有 Git 仓库时，说明现状与采用 Git 对审阅、回退和协作的价值；一次性材料、受其他版本系统管理或不适合纳入 Git 的工作可保持现状。不为完成检查强行初始化。已有仓库不重复初始化；初始化、提交、推送和发布分别判断授权，不能相互推定。

## 在合适节点主动给出提交建议

1. **读取实际状态和内容。** 区分本任务与用户原有/其他任务改动，分别查看已暂存、未暂存和未跟踪文件。不能只凭文件列表归属改动；同一文件可能混合多项工作，必要时逐块核对。未跟踪文件不会自动出现在普通差异中，应另行读取相关内容。
2. **核对验证。** 记录必要检查实际通过、失败和未执行的部分，判断是否有影响使用的已知问题。验证未完成时不把“文件改完”写成可交付。
3. **选择边界。** 判断当前内容是否目标明确、可独立审阅和回退，是否到达值得保留的节点，有无无关改动或未完成部分。
4. **说明建议。** 明确建议现在提交、暂缓或拆分；给出价值或阻碍、必要下一步。建议提交时列准确文件范围，必要时限定到变更块，并给出与实际内容相符的候选提交说明。

可使用环境提供的 Git 接口；以下 CLI 仅为可选只读示例，路径按实际仓库替换：

```text
git rev-parse --show-toplevel
git status --short
git diff --name-status
git diff --cached --name-status
git diff -- README.md
git diff --cached -- README.md
git ls-files --others --exclude-standard
```

若已形成值得独立保存的检查点，即使后续阶段未开始也可建议提交；如果当前组仍有必要验证失败，优先暂缓这组，或拆出已独立完成、验证充分且不依赖失败部分的内容。提出建议无需提交授权，实际执行仍按下节判断。不要按文件数量、固定时长或每次委派机械触发提交。

简短沟通模板（只填实际信息）：

```text
改动：{主要文件/变更块、行为变化及目的}。
验证：{实际通过}；{失败及影响}；{未执行及原因}。
建议：{现在提交/暂缓/拆分}，因为{独立审阅和回退价值或当前阻碍}。
范围：{精确路径，混合文件注明本任务变更块；不含哪些原有改动}。
候选说明：{准确概括当前范围的提交信息}。
下一步：{已有授权内直接执行的事项；确需的新授权或待解决项}。
```

## 建议与执行分开

- 用户尚未授权实际提交时，完成文件修改、验证及可审阅建议即可，不执行提交。已有明确且适用的提交授权时，按范围执行，不重复确认。
- 提交前重新核对实际差异和拟提交范围，使用明确文件清单；不默认 `git add -A`，不默认提交整个索引，不擅自 reset、清空、重建或覆盖用户暂存。
- 用户原有暂存属于另一项工作时，应隔离本任务提交且验证原暂存内容保持。只有在工具可靠支持并核实结果时才采用保留原索引的隔离方法；否则暂缓实际提交，说明原因，不为“清理工作区”移动或取消用户暂存。
- 明确文件路径仍不足以隔离同文件内的混合改动；不能用按路径提交把用户尚未授权的变更一并纳入。先界定变更块和可靠的隔离方式；无法可靠分离则暂缓该文件。
- 已暂存文件不是历史备份，未提交原改动不能假定已存在于 `HEAD`。移动暂存文件仍可能产生旧路径暂存、新路径未跟踪的交接问题；整理时参见 [工作区整理参考](workspace-organization.md)。
- 若执行提交，核对提交内容、提交标识及提交后的工作树/索引，报告实际结果。推送、打发布标签、创建发布或部署按各自适用授权判断，不能由提交授权推出。

## .gitignore：先评估，再由用户裁决

仅在上述触发情形或规则实际影响变化时评估；已有规则足够时直接说明保持现状，避免每次小修改重复询问。不存在 `.gitignore` 也不代表必须建立。

先盘点实际文件与协作需要：

- 读取根级及相关子目录的 `.gitignore`，并留意本地排除和全局忽略是否改变观察结果。
- 区分正式源码、共享配置、输入数据、复现材料、必要日志、可再生缓存和临时产物，核实来源及再生成本。
- 核对已跟踪、已暂存、未跟踪及已忽略状态；判断需要保留到版本库、留在工作区、外部保存或另行备份的对象。
- 检查规则是否会隐藏正式模块（如 `__init__.py`）、必要运行日志、样例数据或复现材料；不要仅按扩展名、文件名或大小推断用途。

形成可审阅的具体方案后，才请求必要的用户决定。方案应包含：

| 项目 | 要说明的具体内容 |
|---|---|
| 支持建立/调整 | 哪些实际缓存、临时文件或受控材料可避免误纳入，当前发生或可能发生的具体问题 |
| 保持/暂缓/缩小范围 | 当前没有此类产物、维护规则的代价、共享配置或复现需要；可用明确提交范围或已有本地排除等替代方式及其局限 |
| 误排除风险 | 是否会隐藏源码、共享配置、必要日志、数据样例或复现证据；规则是否跨目录匹配 |
| 推荐方案及前提 | 保持现状、新建或局部调整；为什么该范围足够、何时应重新评估 |
| 精确规则与影响 | 展示拟写入或删除的实际规则，列应忽略和应保留的代表路径，列已跟踪/暂存对象的另行处理需求 |
| 用户决定状态 | 待裁决、同意、拒绝或指定修改；已有明确决定的适用范围 |

**实际 `.gitignore` 的新建或调整须在用户裁决后执行。** 已有针对该具体方案的明确决定时直接照办，不重复询问；一般“整理项目”或“升级 Skill”不自动包含任意忽略规则变更。用户决定前继续不依赖该决定的工作。待定文件影响提交范围时，暂缓相关提交并说明原因；独立且已验证的工作仍可给出建议。

`.gitignore` 只影响忽略行为，不会自动移除已跟踪文件、取消已有暂存、清除历史记录或替代备份。索引清理、历史清理和备份删除单独判断授权。

## 规则按用途选择，避免通配误伤

没有必须照搬的标准模板。以下是评估候选的例子，只有项目确实采用相应用途且用户决定后才写入实际文件：

| 实际情况 | 可讨论的精确候选 | 要保留/核实的对象 |
|---|---|---|
| 根目录 `scratch/` 全为可丢弃验证产物 | `/scratch/` | 正式脚本、需保留的故障复现材料应有明确归属，不藏在该目录内 |
| 已确认 Python 缓存和本地虚拟环境 | `__pycache__/`、`*.pyc`、`/.venv/` | `.py` 源码及共享依赖声明仍保留 |
| 一个工具的根级预览缓存可再生 | `/.preview/` | 正式导出图表和工具共享配置不因此排除 |
| 某运行目录的调试日志无需共享 | `/runs/local-debug/*.log` | 审计日志、成功/失败执行证据和复现记录按用途保留 |
| 原始数据需外置 | 确定数据路径后给出窄范围规则 | 小型样例、来源、校验和、获取方法及合法共享材料；已有跟踪另行处理 |

不使用 `_*.py`、`_*.ps1` 识别临时脚本：`_*.py` 会误匹配 `__init__.py` 等正式源码。临时用途由已核实目录表达。不要全局忽略 `*.log`，也不要默认排除整个 `data/raw/` 或全部某类科学文件；这些对象可能是必要证据或复现输入。项目级编辑器/工具配置是否共享，依据实际协作需要说明利弊后由用户决定。

## 用户决定后验证实际匹配

应用足够且精确的规则，重新核对差异；用至少一个应忽略对象和一个应保留对象验证，风险涉及日志、源码或数据时分别选代表路径。可选 CLI 示例：

```text
git check-ignore -v -- scratch/example.tmp
git check-ignore -v -- src/package/__init__.py
git ls-files -- src/package/__init__.py
git status --short --ignored
```

`git check-ignore` 对未匹配路径通常返回非零状态，应据输出和退出状态判断，不能把它当工具故障或笼统宣称通过。已跟踪路径默认不会报告忽略匹配；需诊断其“若未跟踪是否会匹配”时，可另用 `git check-ignore --no-index -v -- 路径`，并同时报告真实跟踪状态。无仓库时可在隔离副本中保留相关规则层级进行匹配诊断，或使用实际工具支持的检查；不能为运行示例强行初始化项目。未能验证时明确说明限制，不声称匹配通过。

定位匹配规则的来源，修正方案范围内的误排除；需要超出已决定范围时，先展示新增影响，再由用户裁决。最后报告实际修改、匹配结果、保留对象及仍需另行处理的已跟踪文件，不自动清理索引或历史。
